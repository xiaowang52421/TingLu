下表假设当前运行环境最多 4 个并发 Agent 槽，其中包含主控，因此每批最多 3 个执行角色。实际槽数更多时可以提前符合依赖的工作；槽数更少时缩小批次，角色数量不等于同时运行数量。

## 交接与变更

### 主控的动态调度授权

用户已明确授权：开发正式开始后，主控可以部署、停止/撤销、回收、拆分、合并和重分配子 Agent。无需为常规调度逐次征求许可。发现某任务负载过重、某 Agent 先完成空闲、另一任务停滞或成为瓶颈时，可主动调整；任务耗时较短本身不代表质量已通过，应先核对交付证据。

调度时按以下步骤执行：
1. 核对实际进度、依赖、瓶颈和可用并发槽，判断拆分能否产生独立工作；纯串行或共享文件改动不强行并行。
2. 给新子任务分配唯一标识，如05A、05B，编写并保存完整提示词到docs/upgrade/prompts/dynamic/，包含目标、背景、输入、输出、独占文件/测试范围、接口版本、依赖、验收与交接、模型gpt-6-luna/xhigh。新子任务各写docs/handoffs/UPGRADE_<任务ID>.md，不能共用父角色交接文件；只有发生真实拆分时才建立这些文档。
   同时显式分配互斥测试范围，例如Assets/TingLu/Tests/Upgrade/Role05A与Role05B，或父目录中已明确所有者的互斥子目录；父角色停止写已转交范围。00决定复用原测试asmdef还是新增程序集并维护引用，不因拆分让子Agent自行改共享asmdef；无互斥生产及测试范围时不得并行。
3. 更新所有权与派发登记；原角色与新角色的文件范围必须互斥。必要时让原角色先停止对应文件写入并交接当前状态，再转移所有权。共享契约和启动入口仍由00维护。
4. 向用户简要汇报原因、增撤哪些任务、各自负责什么、提示词路径与预期影响。常规调度报告后可直接执行，无须把“汇报”变成等待批准。
5. 撤销子Agent时先通过工具停止/中断其工作，记录完成/未完成/在途改动并由接手者复核；若工具不支持关闭就标记撤销并停止分配。不得删除已产出文件、重置他人修改或把撤销等同于回滚全部成果。
6. 新任务进入相同交接和验收链；晚到的旧回报先核对任务代际、接口与文件版本，避免覆盖接手者成果。工具不支持指定模型时报告限制并暂停受影响的派发，等待用户决定替代方案；并发槽不足时由主控自主分批并汇报，不伪造已部署。

00 在docs/upgrade/DISPATCH_LOG.md记录实际派发和回收；本文件在开始开发且发生调度后创建，当前文档阶段没有实际部署记录。登记至少含任务标识、父任务、理由、实际模型/effort、提示词路径、独占范围、依赖、状态、成果/交接和用户汇报摘要。

需要用户决定的情形：改变已确认玩法、扩大本轮交付范围、改变目标模型、重要体验取舍、无法从现有信息推断的需求。应提出明确选项、原因和建议，等待回答期间继续不依赖答案的工作。不能因任务变慢就重复询问已确定需求，也不能用调度权限绕过明确暂停/停止指令。

### 标准交接

每个角色提交：
status: READY_FOR_REVIEW | PARTIAL | BLOCKED
role/model/effort: 实际角色、模型与推理设置
contract_version: 实际版本
completed/changed_files: 能力与路径
integration: 组件/构造参数/场景接线
tests: 用例、命令、实际通过/失败/未运行、证据路径

contract_requests: 字段/事件/接口请求及受影响消费者
next_dependencies: 下一步依赖

跨目录问题由当前目录所有者修复。共享契约变更由 00 递增版本并通知受影响角色；必要时暂停该边界的写入，迁移后恢复。主控不得把“角色说完成”当作已集成证据。
