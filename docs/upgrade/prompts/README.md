## 实际使用顺序

1. 先阅读项目根目录 升级文档入口.md 和 docs/upgrade/01_需求与规则.md，核对本轮范围与默认方案。
2. 用户明确开始开发后，在副本 D:\听路_街区升级 中设置主控模型为 gpt-6.1-sol/high，把 00_主控.md 整份交给主控。
3. 主控按[03的G0唯一就绪清单](../03_任务与并行计划.md#g0-唯一就绪清单)逐项发布证据；概述不另构成门槛。首次Unity全量导入由00独占，其他角色不启动第二个编辑器。
4. 主控按03_任务与并行计划.md派发01–12，执行模型统一gpt-6-luna/xhigh。目标模型不支持时报告限制并暂停受影响的派发，等待用户决定替代方案，不能自行换模型。
5. 角色多不表示全部同时运行。按工具可用槽数分批；4槽环境下主控外最多3个执行角色。独立工作可提前，依赖未就绪时只做不依赖实现的准备。
6. 主控接入Bootstrap/共享配置/asmdef；角色不越界。每个角色只写UPGRADE_XX.md交接。
7. 12对可运行版本独立判定A01–A31，00修复、构建并给实际新入口；A32–A34另记未来COMPLIANCE.md。A33在开始开发前冻结为文档阶段历史，不把后续合法开发当作违规。人工画面、音频与鼠标手感未测时明确标注。

所有提示词均带共同规则，可整份复制；它们仍要求读取同一副本中的权威需求/接口/分工/验收文档。不要只发截图或截断一段任务，避免丢失边界。
不需要重新提供原始策划附件给每个角色；副本保留附件供参考，本轮需求优先。

## 主控调度权限与使用方法

用户已授权主控在开发启动后自主部署和撤销子Agent，按需求拆分并行工作、合并任务或重新分配负载。13份角色提示词是基础分工，不是人数上限。某个Agent很快交付时先检查质量，再可安排它接手其他独立工作；某任务过慢或过重时，判断依赖后拆成能并行的子任务。不得为增加人数把串行工作硬拆，实际并行数始终受工具槽位限制。

每次调度必须：

- 写清完整子任务提示词，真实拆分时保存到docs/upgrade/prompts/dynamic/；说明目标、输入/输出、文件权限、接口依赖、验收与交接，执行模型仍为gpt-6-luna/xhigh。
- 更新唯一文件所有权与派发登记，避免多个Agent同时写同一文件；共享契约及启动入口仍由主控负责。
- 向用户汇报调整理由、部署/撤销哪些子任务、分工与提示词位置。常规调度不需逐次申请批准。
- 撤销时停止后续工作并接收现有成果，核对在途修改；不能直接删除该Agent文件或清空已有修改。

示例：记忆角色05成为瓶颈时，可拆为05A“连续覆盖并集”和05B“临时记录局部刷新”，同时分配互斥生产文件与测试范围（如Role05A/Role05B或互斥子目录），父角色停止写移交部分；00决定测试asmdef复用/新增并维护引用。原05或主控负责接合。若瓶颈是同一共享接口未确定，应先解决接口，不重复部署等待者。

主控可在需要时向用户提问确认。玩法方向、范围扩张、目标模型变化或重要取舍等需用户决定；常规分工和调度直接执行并汇报。等待回答时可推进其他独立工作。本权限不改变“当前只写文档”的阶段边界，须先收到正式开始开发指令。

完整流程见[任务与并行计划](../03_任务与并行计划.md)。未来实际调度登记于docs/upgrade/DISPATCH_LOG.md；尚未发生的派发不得写成已执行。
